This page costs <Neon>640,000 database reads</Neon>.

It's a bucket list. Name, region, object count, size. One of our platform
partners renders it every time a customer opens their storage dashboard. For
most of Tigris's life, it was the single most expensive query in our system. Not
object reads. Not multipart uploads. A dashboard.

This post is about why, and about the cache that fixed it. The cache itself is
boring. The interesting part is proving exactly how stale the answer can ever
be.

## Why does one number cost 1,280 reads?

Tigris keeps all of its metadata in FoundationDB: tenants, buckets, IAM,
billing, object rows. Every metadata operation is an ACID transaction. That
includes usage accounting. Every PUT, DELETE, and multipart completion updates a
set of counters for its bucket: row counts, plus byte sizes per storage tier.

Here's the catch. If each counter were a single key, every write to a hot bucket
would fight over the same few keys. The bucket would serialize on its own
bookkeeping. So each counter is sharded across 128 keys instead. A write bumps
one shard, atomically. Writes scale beautifully.

Reads pay the bill. To reconstruct one bucket's size, you read every shard of
every counter. That's roughly 10 counters × 128 shards ≈ <Neon>1,280
reads</Neon>. For one number, on one bucket.

Now multiply by the dashboard. A tenant with 500 buckets triggers 500 × 1,280 ≈

<Neon>640,000 FoundationDB reads per page load</Neon>. At our partner's call
volume, this one path dominated list-buckets latency platform-wide.

Was all that work necessary? Mostly, no. Between two page loads, most buckets
receive zero writes. Their sizes haven't changed. We were recomputing identical
numbers, at five-figure read cost, over and over.

## So why not just make it faster?

The obvious fixes attack the compute path. Make the scan faster. Precompute the
total into one key. But the compute path isn't the problem. The problem is
recomputing values that haven't changed.

What made a cache safe here? A property the metric already had: <Neon>a bucket
size is an approximation the moment it's computed</Neon>. Writes race the
counter scan. Replication lags. Staged bytes come and go. "Approximately right,
as of ten minutes ago" is the same promise as "approximately right, as of now."

That insight did real design work. An early draft added a `with_cached_size`
opt-in flag to the request, plus a "force fresh" escape hatch. Review killed
both. If the number is approximate either way, a knob choosing which
approximation is API surface without a purpose. So the cache became invisible.
Callers change nothing. A per-namespace feature flag turns it on.

## Where does the cache live?

At the gateway edge, in front of the backend that owns the counters. We already
run a regional edge cache there: KVRocks, a RocksDB-backed store that speaks the
Redis protocol, shared by every gateway pod in the region. The bucket-size cache
is a new table in an existing store. No new infrastructure.

The read path has three steps.

<MermaidFrame
  style={{ maxWidth: "40rem", margin: "1.5rem auto" }}
  caption="Most lookups turn around at the edge cache. Only the misses pay the 1,280-read scan."
>
  <CacheFlowDiagram />

First, the gateway asks the backend for the bucket list _without_ sizes. One
cheap range read. Second, it asks the cache for those 500 sizes. Most are
already known. Third, it asks the backend to size only the misses — a single RPC
naming just those buckets — and caches the results with a jittered multi-day
TTL.

That `names` filter is the only proto change in the whole project.

Why does the bulk miss-fill matter? A naive cache fires one backend call per
missed bucket. Fifty misses, fifty RPCs. Ours fires one RPC per page. And the
cached value is the full `BucketMetadata` message, not a hand-projected size
struct, so there's no second schema to keep in sync. On a hit, a helper grafts
the cached size fields onto the fresh listing.

## How do you trust a four-day-old number?

This is the real engineering. The TTL is four days. How do you promise the
number is never _meaningfully_ wrong?

Two layers. And the elegant part is what we didn't build: no invalidation queue,
no tombstone table, no per-bucket cooldown record. No new state anywhere.

<Takeaway
  n={1}
  title="A write shortens the entry's life. It doesn't delete it."
>
  When a size-changing write lands — PUT, DeleteObjects, CopyObject, rename,
  multipart completion — the gateway shortens the cached entry's remaining TTL
  to 15 minutes. But only if it's currently longer. The remaining TTL _is_ the
  cooldown clock. Long TTL? Not invalidated recently; shorten it. Short TTL?
  Already dying; do nothing. One conditional expire encodes the whole rate
  limiter, idempotently, across every pod. (One wrinkle: our deployed KVRocks
  version lacks `EXPIRE ... LT`, so it's a TTL read plus a conditional `Expire`.
  The property survived. The one-liner didn't.)
</Takeaway>

<Takeaway n={2} title="A per-pod debounce absorbs the storm.">
  A bucket taking 100 writes per second would otherwise fire 100 cache
  operations per second. An in-memory LRU keyed by bucket collapses that to
  roughly one operation per cooldown window, per pod. The suppressed writes
  don't even pay a network round-trip. Cross-region writes ride an event that
  already existed for the object cache. No new event type, no producer change.
</Takeaway>

Here is the whole mechanism as it runs in the gateway today, both layers,
lightly renamed for print:

```go
// Invalidate marks the bucket's cached size for refresh. Debounced per pod: a write storm
// (or a stream of cross-region notifies) for the same bucket collapses to ~one cache op per
// cooldown, so it never hammers the network.
func (c *BucketSizeCache) Invalidate(ctx context.Context, tenantID, bucket string) {
	if c.recentlyInvalidated(bucket) {
		return
	}
	_ = c.debounce.Set(bucket, c.now())

	shortened, err := c.shortenTTL(ctx, tenantID, bucket)
	switch {
	case err != nil:
		metrics.Invalidation(outcomeError)
	case shortened:
		metrics.Invalidation(outcomeFired)
	default:
		metrics.Invalidation(outcomeSkipped)
	}
}

// The entry's own remaining TTL is the cooldown clock: shorten to the cooldown only
// when currently longer, so a hot bucket isn't re-invalidated on every write (0 deletes).
func (c *BucketSizeCache) shortenTTL(ctx context.Context, tenantID, bucket string) (bool, error) {
	key := c.cacheKey(tenantID, bucket)
	ttl, err := c.cache.TTL(ctx, key)
	if err != nil {
		return false, err
	}
	if ttl <= 0 || ttl <= c.cfg.Cooldown {
		return false, nil
	}
	return true, c.cache.Expire(ctx, key, c.cfg.Cooldown)
}
```

Every outcome is a metric: fired, skipped, or error. The hit rate, the fallback
count, and the age of served values each get their own series, so "is the cache
healthy" is a dashboard, not a guess.

Together the two layers give you two bounds. The bounds are the point:

- A busy bucket is at most <Neon>~15 minutes stale</Neon>. Sustained writes
  re-converge on schedule, forever.
- A missed invalidation — dropped event, bug, network partition — is bounded by
  the multi-day TTL. The TTL isn't the mechanism. It's the insurance.

What if the cache itself dies? Nothing dramatic. Any cache failure falls back to
the uncached path — the page costs what it cost before the cache existed, and a
fallback metric counts how often that happens. Mass expiry can't stampede the
backend either: every entry's TTL carries a random jitter, so a cold tenant's
refills spread out instead of landing at once. And rollback is a config flip.
Disable the namespace flag, and the next call passes straight through.

## Fifteen ways to be wrong

A multi-day TTL is only safe if you list the ways it can lie to you. The design
doc enumerates fifteen corner cases. Three are worth retelling.

**Delete and recreate.** Delete bucket `photos`. Create a new `photos`. The
hard-delete path emits no cache event — we checked the code rather than assuming
— so the newborn bucket could wear its ancestor's size for days. The defense is
free: the cached value carries the bucket's `created_at`, the fresh listing
carries the new one, and a mismatch counts as a miss.

**Burst, then silence.** A write burst shortens the TTL once. Then the writes
stop, and no future event will ever fire. Without care, the entry would serve
its pre-burst size for days. Shorten-not-delete absorbs this case: the entry
expires within minutes of the burst no matter what, and the next read refills it
fresh.

**The race we kept.** A miss-fill dispatches at T0. A write lands at T1, while
the fill is in flight. The fill returns at T2 and caches the pre-write size,
under a fresh TTL. We considered generation counters, tombstones, and CAS — and
rejected them all. The window is tens of milliseconds. The staleness ceiling is
the same TTL we already accept. The metric is approximate by contract. We
documented the race and moved on.

## What the spec got wrong

Our design doc has an unusual section: as-built annotations, recording where the
implementation diverged from the spec and why. The diffs are the most
instructive part.

The original design stored a `last_modified` timestamp inside the cached value
as the cooldown anchor, with delete-plus-refill semantics. The implementation
replaced it with TTL-shorten plus the debounce. Simpler, one less field, and
burst-then-silence falls out for free instead of needing a special clamp.

We also added a tenant-ID field to the cross-region cache event. One PR later,
we reverted it. The namespace is resolvable from the bucket at handle time, so
it doesn't need to ride every write event in the system. Growing a hot-path
event to save one lookup in a cold handler is the wrong trade. It took a
reviewer to say so.

Specs are hypotheses. The honest changelog is worth more.

## The arithmetic, after

A warm page pays one metadata range read and one batched cache lookup. Zero
counter scans. A cold page adds one bulk miss-fill for the ~50 buckets the cache
doesn't know, each amortized over days of later hits.

The design target was blunt: take roughly <Neon>a million expensive size queries
down to about a hundred</Neon>. Four orders of magnitude, with staleness
provably bounded at 15 minutes for busy buckets and the TTL for pathological
failures.

The cache will also outlive its own backend. The counter scan behind the
miss-fill is slated for replacement by an OLAP-backed size path. When that
lands, only the miss-fill swaps. The cache table, the TTL-shorten, the debounce,
the bounds — all of it carries over. Even a fast analytical backend shouldn't be
asked about buckets that haven't changed.

## Takeaways

<Takeaway
  n={1}
  title="The design that makes writes scale makes reads expensive."
>
  Sharding a counter doesn't remove the cost of aggregation. It hands the cost
  to whoever reads. Know which side of that trade your traffic lives on before
  your dashboard becomes your most expensive endpoint.
</Takeaway>

<Takeaway n={2} title="An approximate metric is a caching license.">
  If callers can't tell "as of now" from "as of 15 minutes ago," refusing to
  cache is pure waste. And skip the force-fresh knob. Nobody needs it, and API
  surface is forever.
</Takeaway>

<Takeaway
  n={3}
  title="The cache is not the engineering. The staleness bounds are."
>
  Anyone can put Redis in front of a slow query. The safe part is the
  enumeration: fifteen corner cases, two provable bounds, and one race accepted
  on purpose, written down where the next engineer can check it.
</Takeaway>
