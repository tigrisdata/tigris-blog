## Your work queue shouldn't sit in a database

There are good reasons why this rule is worth following. For example, a `tasks`
table with a `status` column may look simple at first. However, as activity
picks up, workers start fighting over rows. All of a sudden, you add a reaper
for stuck jobs, then a scheduler for delayed ones, and soon the busiest table in
the system is the queue.

We decided to break this rule on purpose. Our team placed every background task
in Tigris, from replication to billing to lifecycle to webhooks, is a single key
in FoundationDB, and the whole queue is **a sorted range of those keys**. Our
internals do not use a broker or a scheduler as secondary systems.

The rule was written for a different kind of database

However, before we explain how all of this works in detail, let's look at why
the rule existed in the first place.

## Why queues left the database

For a long time, this rule was a mainstay in the industry. Work queues moved out
of the database, [Kafka](https://kafka.apache.org/documentation/#design) made
the log a first-class system, [SQS](https://aws.amazon.com/sqs/) made the queue
a managed service, and keeping work out of your tables became standard practice.

Although moving the queue out solves the contention problem, a new problem is
created in its place. When you place a queue beside the database, you are
maintaining two systems that can fail independently, which is the
[**dual-write problem**](https://www.confluent.io/blog/dual-write-problem/). In
this scenario, the object write can succeed while the enqueue is lost, or the
task can land while the object write aborts. The standard workaround for this is
an outbox table and a reconciliation job, which are both extra machinery just to
keep the two systems in agreement.

## What FoundationDB changes

This is why we decided to use [FoundationDB](https://www.foundationdb.org/) to
solve the issue. We already use it to
[store Tigris metadata](/blog/append-only-storage). It is a distributed
key-value store with strict ACID transactions, and it keeps every key sorted in
one giant ordered keyspace, carved into _subspaces_ by key prefix.

These two properties matter because the failure modes behind the rule come from
workers contending on mutable rows. If keys are ordered and transactions are
strict, nothing needs to be mutated at all.

<PullQuote>
  The queue can just be a range of keys, and the sort order is the schedule.
</PullQuote>

We used this to eliminate the dual-write problem as well. Because the queue
lives in the same database as the metadata, an object write and the background
tasks it creates end up being committed within one transaction only:

```go
txManager.Tx(ctx, func(ctx context.Context, tx kv.Tx) error {
	objMetaManager.Insert(ctx, tx, objMeta) // the object's metadata row
	return queue.EnqueueObjectTasks(ctx, tx, ...) // replication, notifications,
	                                              // billing, lifecycle
})
```

Here you can see how the object and its tasks land together, or neither does.

## Apple broke the rule first

Tigris is not the first company to build a work queue this way. In 2021, Apple
published
[QuiCK: A Queuing System in CloudKit](https://www.foundationdb.org/files/QuiCK.pdf),
describing how iCloud's storage backend queues its background work inside
FoundationDB rather than beside it, at the scale of tens of billions of logical
queues, one per user of every app.

The paper describes how a consumer claims work:

> "When taking a lease, instead of removing the work item from the queue (and
> risking losing it if the consumer fails), we increase the work item's vesting
> time by the lease duration."

They use the terms **vesting time** to describe the moment a task becomes
available. To claim a task, a consumer moves its vesting time forward instead of
locking or flagging it.

We took the API design directly from the paper, including the vocabulary, and
adapted the sharding to our tenancy model.

Let's take a look at the specifics.

## A task is just a key

Every queued task in Tigris is one key-value pair:

```text
("queue", version, taskType, itemSpace, vestingMs, priority, id) → QueueItem
```

There are about ninety different instances of `taskType`. Each is pracitically
its own queue, which is split into 256 partitions we call lanes, with items
hashed to lanes by key.

The entire API on top of the key consists of five verbs:

- Each **enqueue** → a new key at `now + delay`
- Each **peek** → a range read from the start of a lane up to `now`
- Each **claim** → the same key, moved into the future with a fresh lease id
- Each **renewal** → the same move, further into the future
- Each **completion** → a delete

FoundationDB's
[tuple encoding](https://apple.github.io/foundationdb/data-modeling.html) writes
integers big-endian, so byte order matches numeric order. That means that every
lane is already sorted by vesting time, and no process ever sorts the queue.

When vesting time happens, there is not trigger. The timestamp is a position in
the keyspace, and a task vested in the future sits past the edge of every
reader's range until the ranges grow to reach it. Delayed work and retry with
backoff do not take up more resources, since they are just keys placed further
out.

## How workers claim tasks

You will see the biggest difference in how our worker claims a task. A
status-column queue claims a row by flipping its state, and the
[standard Postgres pattern](https://www.postgresql.org/docs/current/sql-select.html)
looks something like this:

```sql
UPDATE tasks SET status = 'running'
WHERE id = (
  SELECT id FROM tasks WHERE status = 'queued'
  ORDER BY run_at LIMIT 1
  FOR UPDATE SKIP LOCKED
) RETURNING *;
```

Tigris claims a task by moving it:

```go
// The core of ObtainLease, trimmed for print:
// delete the row, reinsert it at now + leaseTime.
if err = q.dequeue(ctx, tx, item); err != nil {
	return nil, err
}

item.LeaseId = uuid.NewUUIDAsString()
return item, q.Enqueue(ctx, tx, item, leaseTime)
```

The delete and reinsert happen in one strongly consistent transaction, so it
either works or it doesn't. As a result, tasks can't disappear from the queue.

If two workers race for the same key, FoundationDB's conflict detection lets
exactly one commit. The peek process itself is a snapshot read, so scanning a
lane takes no conflict ranges and never collides with producers.

It's just as simple to recover from failure. For example, consider a worker that
claims a task and gets OOM-killed two minutes into a six-minute lease. On our
side, the lease stops being renewed and the clock passes the vesting time four
minutes later.

The task in question becomes visible to every reader again, ready for the next
worker to pick up. **There is no separate recovery path.** Leases run six
minutes by default and up to 70 for migrations, and long tasks renew at a third
of the interval while checkpointing progress into the payload. Ultimately,
whichever worker picks up an abandoned task, it resumes from the last
checkpoint.

## Where we differ from Apple

This was originally built for Apple's
[CloudKit](https://developer.apple.com/icloud/cloudkit/), where the system runs
billions of tiny queues and finds work by sampling. In this case, consumers pick
a random fraction of pointer entries, and the paper reports what tuning that
fraction costs. Their experiments ran with a fraction of 0.02; raising it to 0.2
made about 44% of lease attempts fail, and 0.5 made about 64% fail.

Tigris' tenant is the task type, and there are about ninety. In our case, we
keep the queue flat and solve collisions structurally: items hash to lanes
deterministically, and a hashring assigns each lane exactly one owner. With one
scanner per lane, collisions at the head of a lane simply do not happen, and
there is nothing to tune. The cost shows up when pods join or leave and the ring
briefly rebalances.

We handle distribution separately as well. QuiCK spreads capacity across users
with a scheme the paper calls water-filling, so one busy user cannot starve the
rest. Our risk is one busy task type, like a backlog of tombstone cleanup
starving billing, so a dispatcher round-robins across task types and the workers
are split into groups that keep cleanup work away from urgent work.

## The rule, rewritten

If you take one thing from this post, let it be the question we asked ourselves:
how much of your queue is real work, and how much is a workaround for a database
that cannot keep order? FoundationDB keeps its keys sorted and its transactions
strict, so for us the answer was almost all of it. The broker, the scheduler,
the reaper, and the outbox all collapsed into one range of keys that moves
through time.
