When you PUT an object into Tigris, the response comes back long before the work
is finished. The object still has to be replicated to other regions, counted for
billing, scheduled for lifecycle transitions, sent to webhooks, and added to
indexes. None of that should run while a client waits, so all of it goes onto a
queue.

Most companies at this point add a queueing system: Kafka, SQS, Redis, a
Postgres table with a `status` column. We didn't add anything. The Tigris queue
is a keyspace inside the same FoundationDB cluster that stores our metadata, and
the entire design can be explained in three sentences:

- A task's key is its schedule.
- Claiming a task means moving it into the future.
- Crash recovery is what happens when nothing happens.

The design is based on Apple's
[QuiCK paper](https://www.foundationdb.org/files/QuiCK.pdf), which describes the
queue that runs inside CloudKit. We
[briefly mentioned this history](https://www.tigrisdata.com/blog/global-replication/)
over a year ago and promised ourselves we'd write it up properly. This is that
post.

The system in this post is the queue that runs every background task in Tigris:
replication, billing, cleanup, notifications. The entire queue is one keyspace
in FoundationDB, where every task is a single key and that key contains the time
when the task becomes ready. A worker takes a task by moving its key into the
future, where no one is looking, and a crashed worker's task comes back on its
own when time catches up with it:

## The consequences of a PUT

One problem decides everything else: when an object write commits, the
background work it implies must become durable _with it_. If the object lands
but the replication task is lost, the object silently never reaches other
regions. If the task lands but the object write aborts, workers search for an
object that does not exist.

With an external queueing system this is the classic dual-write problem, and you
end up building outbox tables and reconciliation jobs to work around it. Because
our queue is a keyspace in the same database as the metadata, the problem does
not exist. The enqueue is a few more writes inside the same transaction:

```go
// Inside the transaction that applies a PUT. Trimmed for print.
tx.Insert(ctx, objectKey, objectMeta)          // the object's metadata row
queue.EnqueueObjectTasks(ctx, tx, ...)         // replication, notifications,
                                               // billing, lifecycle
// One commit. The object and its consequences land together, or neither does.
```

There is no window in which one exists without the other, no reconciliation, no
second system to keep in sync. The queue doesn't need an outbox pattern because
the queue _is_ the outbox. This is QuiCK's core argument against external
queues, and it works in production.

## The queue is one sorted keyspace

Every queued task is one key-value pair. The shape of the key is the design:

```text
("queue", version, taskType, itemSpace, vestingMs, priority, id) → QueueItem
```

And the function that builds it is short enough to quote in full:

```go
func (q *QueueSubspace) getKey(vesting time.Time, priority int64, id string,
	taskTypeID uint8, itemSpace ItemSpace) keys.Key {
	return keys.NewKey(q.SubspaceName, q.KeyVersion, int64(taskTypeID),
		int64(itemSpace), vesting.UnixMilli(), priority, id)
}
```

Reading the tuple left to right:

- **`taskType`** partitions the queue by kind of work. There are around ninety
  task types: replication, TTL expiry, tombstone cleanup, billing rollups,
  migrations, notifications, and so on.
- **`itemSpace`** is a lane. Each task type is sharded across 256 lanes, and an
  item is hashed into a lane by its key. More on why below.
- **`vestingMs`** is the vesting time in Unix milliseconds: the moment this task
  becomes available to work on. The word comes from the QuiCK paper, and it is
  the part of the key that everything else depends on.
- **`priority`** breaks ties between tasks vesting in the same millisecond.
- **`id`** makes the key unique.

A real key, with the values filled in:

```text
("queue", 1, 23, 17, 1754400123456, 0, "d3f7…")
   │      │   │   │        │        │     │
   │      │   │   │        │        │     └ id
   │      │   │   │        │        └ priority 0
   │      │   │   │        └ vesting: 2026-08-05 14:02:03.456 UTC, in ms
   │      │   │   └ lane 17
   │      │   └ task type 23
   │      └ key layout version
   └ subspace
```

The integers are encoded so that byte order matches numeric order. That is the
property the whole design leans on: FoundationDB compares bytes, and the bytes
compare like times.

FoundationDB keeps keys sorted. That single property, plus this key shape, means
that within any lane the tasks sit in vesting order, oldest first, without
anyone sorting anything. The keyspace is the schedule.

One thing the vesting time is _not_: a trigger. Nothing fires when that moment
arrives. There is no timer, no cron thread, no scheduler component anywhere in
the system. The timestamp is a coordinate, and everything else in this post is
about what you can do with coordinates.

The full API on top of this key is five verbs:

| Verb         | What it actually is                                                  |
| ------------ | -------------------------------------------------------------------- |
| Enqueue      | Insert a key at `now + delay`                                        |
| Peek         | Range-read a lane from the beginning of time up to `now`             |
| Obtain lease | Delete the key, reinsert it at `now + leaseTime` with a new lease id |
| Renew lease  | Same move, further forward                                           |
| Complete     | Delete the key                                                       |

Every one of them is ordinary reads and writes inside an ordinary FoundationDB
transaction. That table is the entire queueing system.

## "What is ready?" is a range read

A worker looking for work does not query a status. It reads a stretch of
keyspace:

```go
// Peek, trimmed for print.
currentTime := time.Now()

startKey := q.getKey(minVestingTime, 0, "", taskType.ID(), itemSpace)
endKey := q.getKey(currentTime, maxPriority, maxId, taskType.ID(), itemSpace)

iter, err := tx.ReadRange(ctx, startKey, endKey, kv.ReadRangeOptions{...})
```

Everything from the left edge of the lane up to the reader's own `now` is ready
work, sitting in one contiguous run of keys. Everything to the right of `now` is
invisible, not because anything filters it out, but because the range read
simply ends before reaching it.

Two details matter here. First, `minVestingTime` is a hardcoded constant, a date
in March 2023 before which no queue item can exist. The left edge of time, in
this system, is a config value. Second, `now` is whatever the _reading_ machine
thinks it is. The queue has no opinion about the present; each reader constructs
its own and asks for everything before it.

Delaying work costs nothing extra. Want a task to run in four hours? Enqueue it
with a vesting time four hours out. It sits to the right of every reader's
window until the windows move past it. Retry with backoff is the same trick with
smaller numbers.

FoundationDB has watches, which push a notification when a key's value changes,
and we do not use them here. A watch fires on a write, and the event this queue
cares about is not a write: a task becomes ready when the clock passes its
vesting time, and nothing in the database changes at that moment. There is no
mutation to watch. Polling a range that ends at now is the natural way to
observe a condition that time creates, and it costs one range read per lane.

## Claiming a task means moving it into the future

The part we find beautiful is what a claim is. When a worker claims a task, it
does not mark the task as claimed, because there is no `status` field, no lock,
and no ownership table to mark. Instead, the worker deletes the row and
reinserts it at `now + leaseTime`, with a fresh lease id:

```go
// The core of ObtainLease, trimmed for print.
if found.LeaseId != item.LeaseId || !found.Vesting.Equal(item.Vesting) {
	return nil, ErrClaimed // someone else moved it first
}

if err = q.dequeue(ctx, tx, item); err != nil {
	return nil, err
}

item.LeaseId = uuid.NewUUIDAsString()
return item, q.Enqueue(ctx, tx, item, leaseTime)
```

That one move does everything a lock manager would do. The row now sits past
every reader's window, so no other worker can see it, let alone claim it. And if
two workers race to claim the same row, FoundationDB's transaction conflict
detection guarantees exactly one of the two commits. The loser's transaction
aborts, it re-peeks, and the row is gone. Mutual exclusion without a mutex.

The same conflict detection has a cost. Peek reads the visible range without
snapshot isolation, so the claiming transaction conflicts with any write that
lands inside that window before it commits. Two properties keep this rare. The
window ends at the scanner's own now, and new work is enqueued at or after the
producer's now, so fresh tasks normally land to the right of the window rather
than inside it. And because each lane has exactly one scanner, the classic
failure mode of queue-on-database designs, every consumer conflicting with every
other at the head of the queue, cannot happen at all.

Ownership checks also work by position. When a worker comes back to renew or
complete, it verifies that the row still carries its lease id and the vesting
time it set. If either has changed, something else has taken the task, and the
worker abandons its claim.

How long is a lease? It depends on the work, and the durations are hardcoded per
task type:

| Work                                   | Lease      | Why                                           |
| -------------------------------------- | ---------- | --------------------------------------------- |
| Small metadata changes                 | 30 seconds | A few reads and writes, finished quickly      |
| Most background tasks                  | 6 minutes  | The default                                   |
| Bucket-wide operations                 | 20 minutes | Scans that touch a whole bucket               |
| Migrations, block transfers, backfills | 70 minutes | Long metadata scans and object data transfers |

Anything that only touches metadata is quick. The long leases exist for work
that scans large ranges or moves object data between regions. A worker on a long
task renews its lease at a third of the lease interval, each renewal being the
same delete-and-reinsert move, and checkpoints its progress into the task
payload as it goes. If a successor ever picks the task up, it resumes from the
cursor instead of starting over.

The lease duration is really a dial with duplicate work on one side and recovery
latency on the other, which brings us to the crash.

## When a worker dies, nothing happens

The oldest comment in the queue's source file says it better than we can:

> If the worker fails to complete the item, the vesting time will eventually
> reach the current time and be visible to other workers to claim and work on.

To see why, follow a single task through a crash. A worker claims it, moving it
six minutes into the future, and two minutes in, the pod is OOM-killed. What
happens next is nothing. No component notices. No alert fires, no reaper sweeps,
no lease table is reconciled, because none of those things exist. The dead
worker simply stops pushing the row forward, and the clock keeps doing the only
thing clocks do. Four minutes later the row's vesting time is in the past, which
means it is inside every reader's Peek window again, which means it is ready
work.

The reason no recovery machinery exists is that there is nothing to recover.
"Abandoned" and "ready" are the same state, a key sitting to the left of `now`,
and the system cannot tell them apart because there is no difference to tell.
Failure detection would be code that distinguishes two identical things.

This robustness has a price. Delivery is at-least-once: a task whose worker died
mid-run will run again, and a task whose worker stalled past its lease can even
have side effects committed by two workers. Every task in the system is
therefore written to be idempotent. That is the contract. And worst-case
recovery latency equals the remaining lease time, which for a migration task can
be almost an hour. That is the dial from the previous section, set deliberately,
task type by task type.

## The paper we took it from

In 2021, Apple published
[QuiCK: A Queuing System in CloudKit](https://www.foundationdb.org/files/QuiCK.pdf),
describing how iCloud's storage backend queues its own background work inside
FoundationDB rather than beside it. The core move is the one you have just read:

> "When taking a lease, instead of removing the work item from the queue (and
> risking losing it if the consumer fails), we increase the work item's vesting
> time by the lease duration."

We took a lot from the paper directly, including its vocabulary. The first
version of our queue had a single narrow job, backfilling secondary indexes. It
worked well enough that we kept finding new work to put on it, and it grew into
the general system that now carries everything from replication to billing.

But Tigris is not CloudKit, and the differences taught us as much as the paper
did.

| Dimension        | QuiCK                                        | Tigris                                 |
| ---------------- | -------------------------------------------- | -------------------------------------- |
| Unit of sharding | User × app: tens of billions of queues       | Task type × lane: ~90 × 256            |
| Structure        | Two levels: queue zones plus a pointer queue | One flat keyspace                      |
| Finding work     | Consumers sample pointers at random          | A hashring gives each lane one owner   |
| Fairness         | Per tenant, via water-filling                | Per task type, via a dispatcher        |
| Storage layer    | Record Layer (indexes maintained for you)    | Raw key-value (every move is explicit) |

The structural difference explains most of the rest. CloudKit gives every user
of every app a logical database, so Apple's queue is really tens of billions of
tiny queues, and they need a second level, a cluster-wide pointer queue indexing
which user queues are non-empty, just to find the work. Our tenant is the task
type, of which there are about ninety, so the queue can stay flat.

The most interesting difference is contention. Both systems face the same
problem: if every consumer reaches for the head of the same queue, they collide.
Apple solves it statistically. Their consumers sample a random fraction of
pointers, and the paper is honest about the cost of getting that fraction wrong:
at their default of 0.02 things behave, but push it to 0.2 and about 44% of
lease attempts fail on conflicts, at 0.5 about 64% fail.

We solved it structurally instead, in two steps, both recorded in our commit
history. First, the queue space was sharded: by task type, then into lanes, with
items hashed to lanes by key. We started with 64 lanes per task type and later
widened to 256 when conflicts returned at higher load. Second, worker pods
coordinate through a hashring that assigns each lane exactly one owner. One
scanner per lane means the collision rate at the head of a lane is not a tuning
parameter, it is zero, and the price is paid elsewhere: a brief window of
contention when pods join or leave and the ring rebalances.

The fairness problem also changed for the same reason. QuiCK's water-filling
exists so that one very busy user cannot starve the rest. Our risk is one very
busy _task type_, a tombstone-cleanup backlog starving billing, so a dispatcher
round-robins across task types when feeding workers, and the workers themselves
are split into groups, garbage collection separate from slow scans separate from
the hot path, so that cleanup work can never block urgent work.

## Two things the paper doesn't have

**Permanent tasks.** Our object-notification worker reads a change log, sends
webhooks, and then re-enqueues itself a few minutes into the future. It never
completes. It is a task that has been in the queue since the feature shipped and
will remain there until notifications are disabled: a cron job implemented as a
single row orbiting just ahead of the readers, forever.

**Unique tasks.** Some producers naturally enqueue the same logical work twice;
the lifecycle scanner rediscovers the same bucket every pass. For those task
types the queue keeps a small side index keyed by task id, and enqueue inserts
into it first. FoundationDB's insert fails cleanly on a duplicate key, and when
it does, the enqueue is skipped. At most one live instance per task, enforced by
the same database in the same transaction.

## The bill

Nothing above is free.

**At-least-once means what it says.** There is no fencing token. A worker that
stalls past its lease and wakes up confused can still commit side effects after
a rival has claimed the row. Idempotent task design absorbs this, but "absorbs"
means the duplicate work happens and is harmless.

Wall clocks create the coordinates. Vesting times come from `time.Now()` on
whichever machine writes the row, so clock skew physically displaces work in the
keyspace. In several years of production this has never actually caused a
problem; the same idempotency that absorbs retries also absorbs work that
arrives slightly early, and NTP keeps the skew small. No need to buy atomic
clocks just yet.

**FoundationDB transactions last five seconds. Our leases last seventy
minutes.** This sounds like a contradiction and is the design's central trick.
Transactions only ever perform the _move_: claim, renew, complete, each a few
milliseconds of reads and writes. The hours of actual work happen outside any
transaction, and the row's position in the keyspace is the durable record of who
is doing what until when.

Some questions are expensive to ask. "How big is the queue?" has no cheap
answer. Counting means range-scanning the whole queue space, and the obvious
fix, an atomic counter incremented on enqueue, would concentrate every
producer's writes onto one hot key, which is precisely the contention this
design exists to avoid. We ended up estimating queue depth rather than measuring
it, and what we do with that estimate, rate-limiting our own workers before they
hurt the database, is a story for its own post.

## When one write becomes five: the log

The queue's real cost at scale turned out to be none of the above. It was write
amplification of a simpler kind: a single object write fanned out into three to
five queue writes, one per downstream concern, region distribution and
notifications and billing each getting their own task row inside the commit.

So a log grew next to the queue. An object write now appends one record to a log
keyspace, and the background consumers each read that log at their own offset
and fan out from there. Marking work as done means moving a cursor forward. And
the log's keys are built on FoundationDB versionstamps, which the database
assigns at commit time in commit order, so the log is ordered by _when things
actually happened_ rather than by what any wall clock claimed. The queue plays
one more part here: the consumers that read the log are themselves queue tasks,
of the permanent kind from two sections ago.

An ordered, immutable stream also turned out to be easier to reason about during
incidents than a queue whose rows keep moving. The log deserves its own post,
and it will get one.

## One database, a long way

A small team needed background processing for an object storage platform and got
it from infrastructure it was already running, with a guarantee that is hard to
find anywhere else. Tasks enqueue atomically with the data changes that cause
them, because they are writes in the same transaction.

The system that started as an index-backfill tool grew to carry everything, one
small adjustment at a time.

Underneath all of it sit the three sentences from the top. A task's key is its
schedule, so there is no scheduler. Claiming a task means moving it into the
future, so there are no locks. And crash recovery is what happens when nothing
happens, because in a sorted keyspace, a task nobody is pushing forward does not
need to be rescued. It just needs everyone else to catch up to it.
