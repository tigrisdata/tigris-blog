When you PUT an object into Tigris, the response comes back before the work is
finished. The object still has to be replicated to other regions, counted for
billing, scheduled for lifecycle transitions, sent to webhooks, and added to
indexes. None of the work should run while a client waits, so all of it goes
onto a queue.

Most companies add a queueing system at that point, e.g., Kafka, SQS, Redis, or
a Postgres table with a `status` column. We didn't add anything. The Tigris
queue is a keyspace inside the same FoundationDB cluster that stores our
metadata, and every queued task is a single key that sorts by its vesting time,
which is the moment the task becomes available to work on.

{/* truncate */}

Three properties of the key explain the whole design:

- The key sorts by vesting time, so the keyspace holds the schedule and no
  scheduler component exists.
- A worker claims a task by rewriting its key with a later vesting time, so no
  lock and no status field exist.
- A task whose worker died becomes ready again once the clock passes its vesting
  time, so no recovery process exists.

The design comes from Apple's
[QuiCK paper](https://www.foundationdb.org/files/QuiCK.pdf), which describes the
queue that runs inside CloudKit.

## Why the enqueue happens inside the object write

When an object write commits, the background work it implies has to become
durable at the same moment. If the object lands and the replication task is
lost, the object never reaches other regions and nothing reports the failure. If
the replication task lands and the object write aborts, workers look for an
object that does not exist.

A separate queueing system gives you the dual-write problem, where two systems
can fail independently and you work around it with an outbox table and a
reconciliation job. Because our queue is a keyspace in the same database as the
metadata, the enqueue is a few more writes inside the same transaction:

```go
// Inside the transaction that applies a PUT.
tx.Insert(ctx, objectKey, objectMeta)          // the object's metadata row
queue.EnqueueObjectTasks(ctx, tx, ...)         // replication, notifications,
                                               // billing, lifecycle
// One commit. The object and its consequences land together, or neither does.
```

The object and its tasks commit together or not at all, so there is no window in
which one exists without the other, and there is no reconciliation job and no
second system to keep in sync. QuiCK makes the same argument against external
queues.

## The queue is one sorted keyspace

Every queued task is one key-value pair, and the shape of the key carries the
design:

```text
("queue", version, taskType, itemSpace, vestingMs, priority, id) → QueueItem
```

Reading the tuple left to right:

- `taskType` partitions the queue by kind of work. There are around ninety task
  types, e.g., replication, TTL expiry, tombstone cleanup, billing rollups,
  migrations, and notifications.
- `itemSpace` is a lane. Each task type is sharded across 256 lanes, and an item
  is hashed into a lane by its key. More on why below.
- `vestingMs` is the vesting time in Unix milliseconds, e.g., 1754400123456 for
  2026-08-05 14:02:03.456 UTC. The word comes from the QuiCK paper, and every
  other part of the design depends on the field.
- `priority` breaks ties between tasks that vest in the same millisecond.
- `id` makes the key unique.

The integers are encoded so that byte order matches numeric order, and
FoundationDB keeps keys sorted by byte order. Within any lane the tasks
therefore sit in vesting order, oldest first, and no process ever sorts them.

Nothing fires when a vesting time arrives, because the system has no timer, no
cron thread, and no scheduler component anywhere in it. The vesting time is a
coordinate in the keyspace rather than an event.

The whole API on top of the key is five verbs:

| Verb         | What it does                                                            |
| ------------ | ----------------------------------------------------------------------- |
| Enqueue      | Insert a key at `now + delay`                                           |
| Peek         | Range-read a lane from the start of the lane up to `now`                |
| Obtain lease | Delete the key and reinsert it at `now + leaseTime` with a new lease id |
| Renew lease  | The same delete and reinsert, further forward                           |
| Complete     | Delete the key                                                          |

Every verb is ordinary reads and writes inside an ordinary FoundationDB
transaction.

## Finding ready work with a range read

A worker looking for work does not query a status field. It reads a stretch of
keyspace:

```go
currentTime := time.Now()

startKey := q.getKey(minVestingTime, 0, "", taskType.ID(), itemSpace)
endKey := q.getKey(currentTime, maxPriority, maxId, taskType.ID(), itemSpace)

iter, err := tx.ReadRange(ctx, startKey, endKey, kv.ReadRangeOptions{
	Snapshot: false, // a real read: this takes a conflict range
})
```

Everything from the start of the lane up to the reader's own `now` is ready
work, and it sits in one contiguous run of keys. Everything after `now` is
invisible, because the range read ends before reaching it.

The right edge of the range is the reader's own `now`, which is whatever the
reading machine thinks it is, because the queue holds no opinion about the
present and each reader constructs its own. Delaying work therefore costs
nothing extra. For example, to run a task in four hours, enqueue it with a
vesting time four hours out, and it stays outside every reader's range until the
ranges move past it. Retry with backoff is the same mechanism with smaller
delays.

We poll rather than subscribe, even though FoundationDB has watches that push a
notification when a key's value changes. A watch fires on a write, and a task
becomes ready when the clock passes its vesting time, which is not a write and
changes nothing in the database. Polling a range that ends at `now` is therefore
the way to observe a condition created by time, and it costs one range read per
lane.

## Claiming a task by moving its vesting time forward

A worker claims a task by deleting the row and reinserting it at
`now + leaseTime` with a fresh lease id. There is no status field to set, no
lock to take, and no ownership table to write to:

```go
// The core of ObtainLease.
if found.LeaseId != item.LeaseId || !found.Vesting.Equal(item.Vesting) {
	return nil, ErrClaimed // someone else moved it first
}

if err = q.dequeue(ctx, tx, item); err != nil {
	return nil, err
}

item.LeaseId = uuid.NewUUIDAsString()
return item, q.Enqueue(ctx, tx, item, leaseTime)
```

The claimed row now sits after every reader's range, so no other worker can see
it or claim it. And if two workers race to claim the same row, FoundationDB's
transaction conflict detection lets exactly one of them commit, so the loser's
transaction aborts and the row is gone when it peeks again.

The same conflict detection has a cost. Peek reads the visible range without
snapshot isolation, so the claiming transaction conflicts with any write that
lands inside the range before the claim commits. In practice the conflict is
rare, because the range ends at the scanner's own `now` and new work is enqueued
at or after the producer's `now`, so fresh tasks normally land after the range
rather than inside it. Moreover, each lane has exactly one scanner, so consumers
never conflict with each other at the head of a lane, which is the usual failure
mode of queue designs built on a database.

Ownership checks work by position too. When a worker comes back to renew or
complete a task, it checks that the row still carries its lease id and the
vesting time it set. If either has changed, another worker has taken the task,
and the first worker abandons its claim.

Lease durations depend on the work, and they are hardcoded per task type:

```go
LEASE_TIME                       = 6 * time.Minute // the default
CHANGE_LEASE_TIME                = 30 * time.Second
MIGRATION_TASK_LEASE_TIME        = 70 * time.Minute
BUCKET_TASK_LEASE_TIME           = 20 * time.Minute
BLOCK_TASK_LEASE_TIME            = 70 * time.Minute
TEST_TASK_LEASE_TIME             = 2 * time.Second
BUCKET_INDEX_BACKFILL_LEASE_TIME = 70 * time.Minute
```

Anything that only touches metadata is quick, and the long leases exist for work
that scans large ranges or moves object data between regions. A worker on a long
task renews its lease at a third of the lease interval, and each renewal is the
same delete and reinsert. The worker also checkpoints its progress into the task
payload, so a later worker that picks the task up resumes from the checkpoint
instead of starting over.

The lease duration trades duplicate work against recovery latency. A short lease
brings a crashed worker's task back sooner, and it also makes a slow worker more
likely to lose its claim while it is still working.

## What happens when a worker dies

A task whose worker died becomes ready again with no intervention, and the
clearest way to see it is to follow a single task through a crash. First, a
worker claims the task, which moves its vesting time six minutes ahead. Second,
two minutes later the pod is OOM-killed, and no component notices, because the
system has no alert, no reaper, and no lease table to reconcile. Third, the dead
worker stops renewing the lease, so the vesting time stays where the worker left
it, and four minutes later the clock passes it. The row is then inside every
reader's Peek range again, which means any worker can pick it up as ready work.

No recovery machinery exists because there is nothing to recover. Abandoned and
ready are the same state, which is a key sitting before `now`, and the system
cannot tell the two apart because there is no difference between them.

The price of the robustness is duplicate work. Delivery is at-least-once, so a
task whose worker died mid-run will run again, and a task whose worker stalled
past its lease can have its side effects committed by two workers. Every task in
the system is therefore written to be idempotent. Worst-case recovery latency
equals the remaining lease time, which for a migration task can be almost an
hour, so we set the lease deliberately for each task type.

## Permanent tasks and unique tasks

Permanent tasks never complete. Our object notification worker reads a change
log, sends webhooks, and then re-enqueues itself a few minutes into the future.
One such row has been in the queue since the feature shipped and will stay there
until notifications are disabled, so it runs as a cron job made of a single row.
Even `Complete` refuses to delete it:

```go
if IsPersistent(item.TaskType) {
	_, err := q.RenewLease(ctx, tx, found, PersistentRequeueDelay)
	return err // re-enqueued a few minutes ahead, not deleted
}
```

Unique tasks exist because some producers naturally enqueue the same logical
work twice, e.g., the lifecycle scanner rediscovers the same bucket on every
pass. For those task types the queue keeps a small side index keyed by task id,
and enqueue inserts into the side index first. FoundationDB's insert fails
cleanly on a duplicate key, and the enqueue is skipped when it does:

```go
if err := tx.Insert(ctx, idKey, tableData); errors.Is(err, kv.ErrDuplicateKey) {
	return nil // already queued once; that is enough
}
```

At most one live instance of the task exists, enforced by the same database in
the same transaction.

## Where our queue differs from the QuiCK paper

In 2021, Apple published
[QuiCK: A Queuing System in CloudKit](https://www.foundationdb.org/files/QuiCK.pdf),
which describes how iCloud's storage backend queues its own background work
inside FoundationDB rather than beside it. The paper describes the same claim
mechanism:

> "When taking a lease, instead of removing the work item from the queue (and
> risking losing it if the consumer fails), we increase the work item's vesting
> time by the lease duration."

We took a lot from the paper directly, including its vocabulary. The first
version of our queue had one narrow job, which was backfilling secondary
indexes, and it worked well enough that we kept finding new work to put on it
until it carried everything from replication to billing.

Our queue diverges from QuiCK in five places:

| Dimension        | QuiCK                                         | Tigris                                   |
| ---------------- | --------------------------------------------- | ---------------------------------------- |
| Unit of sharding | User × app, so tens of billions of queues     | Task type × lane, so ~90 × 256           |
| Structure        | Two levels, queue zones plus a pointer queue  | One flat keyspace                        |
| Finding work     | Consumers sample pointers at random           | A hashring gives each lane one owner     |
| Fairness         | Per tenant, via water-filling                 | Per task type, via a dispatcher          |
| Storage layer    | Record Layer, which maintains indexes for you | Raw key-value, so every move is explicit |

The difference in sharding explains most of the rest. CloudKit gives every user
of every app a logical database, so Apple's queue is really tens of billions of
tiny queues, and they need a second level just to find the work in them, which
is a cluster-wide pointer queue indexing which user queues are non-empty. Our
tenant is the task type, of which there are about ninety, so our queue can stay
flat.

Both systems have to stop consumers from colliding at the head of the same
queue. Apple solves it statistically, because their consumers sample a random
fraction of pointers, and the paper is honest about the cost of getting the
fraction wrong. At their default fraction of 0.02 the conflict rate stays low.
Raising the fraction to 0.2 makes about 44% of lease attempts fail on conflicts,
and raising it to 0.5 makes about 64% fail.

We solved it structurally instead, and our commit history records both changes.
First, we sharded the queue space by task type and then into lanes, with items
hashed to lanes by key. The lane assignment is one small function:

```go
func GenItemSpace(itemKey string) ItemSpace {
	hash := fnv.New32a()
	hash.Write([]byte(itemKey))

	return ItemSpace(hash.Sum32()%uint32(MaxEnqueueItemSpace-MinItemSpace)) + MinItemSpace
}
```

The hash is deterministic where Apple's selection is random, so the same key
always lands in the same lane. We started with 64 lanes per task type and later
widened to 256 when conflicts returned at higher load.

Second, worker pods coordinate through a hashring that assigns each lane exactly
one owner. One scanner per lane makes the collision rate at the head of a lane
zero rather than a tuning parameter, and the price is paid elsewhere, in a brief
period of contention when pods join or leave and the ring rebalances.

Fairness changed for the same reason. QuiCK's water-filling exists so that one
very busy user cannot starve the rest, and our risk is one very busy task type,
e.g., a backlog of tombstone cleanup starving billing. A dispatcher round-robins
across task types when it feeds workers, and the workers are split into groups
so that cleanup work can never block urgent work.

## Costs and limits of the design

The design has costs, and each one below has shown up in our production system.

<Takeaway n={1} title="At-least-once delivery has no fencing token.">
  A worker that stalls past its lease can still commit side effects after
  another worker has claimed the row. Idempotent task design absorbs the
  duplicate, which means the duplicate work happens and is harmless.
</Takeaway>

<Takeaway n={2} title="Wall clocks create the coordinates.">
  Vesting times come from `time.Now()` on whichever machine writes the row, so
  clock skew physically displaces work in the keyspace. In several years of
  production the skew has never caused a problem, because NTP keeps it small and
  the same idempotency that absorbs retries also absorbs work that arrives
  slightly early.
</Takeaway>

<Takeaway
  n={3}
  title="Transactions last five seconds and leases last seventy minutes."
>
  The two limits do not conflict, because transactions only ever perform the
  move. A claim, a renewal, and a completion are each a few milliseconds of
  reads and writes. The hours of actual work happen outside any transaction, and
  the row's position in the keyspace is the durable record of who is doing what
  until when.
</Takeaway>

<Takeaway n={4} title="Measuring queue depth is expensive.">
  Counting the queue means range-scanning the whole queue space. The obvious
  fix, an atomic counter incremented on enqueue, would concentrate every
  producer's writes onto one hot key, which is precisely the contention the
  design exists to avoid. We ended up estimating queue depth rather than
  measuring it, and we use the estimate to rate limit our own workers before
  they hurt the database.
</Takeaway>

<Takeaway n={5} title="One object write became three to five queue writes.">
  Write amplification turned out to be the queue's largest cost at scale,
  because region distribution, notifications, and billing each got their own
  task row inside the commit. An object write now appends one record to a log
  keyspace instead, keyed by FoundationDB versionstamps so the log is ordered by
  commit order rather than by any wall clock, and each consumer reads the log at
  its own offset. The log deserves its own post, and it will get one.
</Takeaway>

## Summary

Tigris gets its background processing from infrastructure it was already
running. Tasks enqueue atomically with the data changes that cause them, because
the tasks are writes in the same transaction. The system started as a tool for
backfilling indexes and now carries every background task we run.

Underneath all of it sit the three properties from the top. The key sorts by
vesting time, so there is no scheduler. A worker claims a task by moving its
vesting time forward, so there are no locks. And a task nobody renews becomes
ready again when the clock passes its vesting time, so there is no recovery
process.
